# Security review: Team 1 Sprint 10 extension modules

One review for the four extension modules that share the Trade REST API process: Customer Preferences, Customer Notifications, Watchlists and Price Alerts, and Portfolio and P&L. The modules sit behind one token verifier, one database and one Kafka broker, so most findings belong to more than one module. Each row names the modules it applies to and says where a category landed differently between them.

| A01 Broken access control | All four | Yes | **Existing routes.** Every `/api/v1/` request passes `JwtVerificationFilter` (`shouldNotFilter` only skips `OPTIONS` and non-`/api/v1/` paths). The per-account routes compare the token's `accountId` claim to the path account inside the service and refuse with `ACC-403`: `AccountService.resolve` (balance, portfolio, order history, notifications), `OrderService.placeOrder` and `cancel`, `WalletTransferService.transfer`. The legacy `/api/clients` and `/api/bank-accounts` routes use `AccessGuard`, and `AccessGuard.isAdmin()` lets a token with role `ADMIN` bypass the owner check. `HeaderTokenAccountIdResolver` decodes the claim without verifying the signature; it is safe only because the filter has already rejected unverified tokens on every `/api/v1/` path. `MarketController` returns market data to any valid token, which is public reference data. **Internal paths.** There is no route under `/api/v1/` for preference resolution or alert delivery: both seams are Java interfaces ([`decision-log/0006`](../decision-log/0006-watchlists-delivers-via-a-java-interface-not-an-http-route.md)), and a grep of the Trade API source finds no `internal` route (E4). **New routes.** The proposed routes for Preferences, Notifications, Watchlists and Portfolio (scope document, section 2) each take the account from the path and must compare it to the verified claim | Existing routes: **accepted** — the owner checks hold, and the admin bypass applies only to the legacy client and bank-account routes, which this sprint does not touch. The unverified decode in `HeaderTokenAccountIdResolver` is **mitigated** by the filter and **not used by the new modules** (they read `JwtRequestContext` claims). New modules: **Verify at build** — no admin bypass on any new route (a customer's data is returned to that customer only); a cross-account test for every route, token for account A against path account B, expecting `ACC-403` (P1); a source check that no `@RequestMapping` method exists for resolve or deliver (P3); and that no module imports another except through the two seams (P2). See O6–O9 |
| A02 Cryptographic failures | Platform; Preferences, Notifications | Yes | `JwtValidator` pins `HS256` and rejects any other `alg` before verifying (line 44); the secret is read from the TrustMe vault (`JWT_SECRET`, documented as 32+ characters; the value itself was not read in this review). **Issuer is not checked:** `JwtValidator` stores `expectedIssuer` but `JWT.require(algorithm).build()` has no `withIssuer`, so a token signed with the shared secret is accepted whatever its `iss`. **Secret material in git:** `leapcapstoneteam1-720d03.TM` is tracked in the repository (first added in commit `f743c21`), is named by `trustme.key-file` in `application.properties`, and begins with the bytes `TMKF`. **Data in transit:** the Kafka broker in `Application/Infrastructure/Kafka/docker-compose.yml` runs `PLAINTEXT` for every listener and publishes `9092` on the host. **Personal data in the new modules:** email and phone have one stored copy in `auth_db.users` ([`decision-log/0003`](../decision-log/0003-preferences-owns-contact-details-other-modules-reference-them.md)); Kafka payloads and notification messages must not carry credentials or card numbers | Issuer: **open**, O1 (one-line fix: `.withIssuer(expectedIssuer)`). Committed vault file: **open**, O2 — the team must either remove it from history and rotate every secret it protects, or record that the repository is private and accept the exposure. Kafka plaintext: **accepted** for the local and classroom broker; residual risk is that anyone on the network can read or publish to topics, which is why A08 treats event contents as untrusted. New modules: **Verify at build** — no second copy of an address anywhere (ledger stores the resolved address only on the row, per [`0004`](../decision-log/0004-notifications-holds-messages-as-pending-channel-when-no-preference-is-stored.md)); no address, token or card data in any Kafka payload or message body (P5); `ResolvedChannel.toString()` masks the address so a logged object cannot leak it |
| A03 Injection | All four | Yes | Every mapper in `Application/Services/order-service` binds with `#{}`; a search of the Trade API and executor sources for `${` in SQL finds only Spring `@Value` placeholders and no mapper (E3). `NotificationMapper.listForAccount` binds `accountId` and `limit`. User-supplied symbols are validated against the instrument table before use (`CandleService`) and reach Fauxnance only as an encoded path variable. The Angular app has no `innerHTML` or `bypassSecurityTrust*` (E10). **New in this sprint:** notification and alert text is built from values a customer influences (symbol, threshold), and email has header-injection risk (CR/LF in a subject or recipient) | Existing code: **no finding**, evidenced by E3 and E10. New modules: **Verify at build** — every new statement binds with `#{}` and no dynamic `ORDER BY`; the `payload` JSONB is bound as a parameter; email subjects and bodies are built from fixed templates with symbol and numbers inserted as plain text, recipient taken only from the resolver, and CR/LF stripped from anything inserted into a header; Angular renders notification text with interpolation only (P5, P8) |
| A04 Insecure design | All four; notably Notifications, Watchlists | Yes | The design closes the volume and replay risks that would be easy to leave open: alerts fire once and re-arm explicitly ([`0005`](../decision-log/0005-a-price-alert-fires-once-then-deactivates.md)); notifications are keyed on `event_id` so a replay is a no-op and a missing preference holds the message rather than dropping it or sending on a default ([`0004`](../decision-log/0004-notifications-holds-messages-as-pending-channel-when-no-preference-is-stored.md)); each extension has its own consumer group ([`0002`](../decision-log/0002-one-consumer-group-per-extension-module.md)); a per-account cap on alerts and a 10 000-row cap on pending notifications. **A design risk that is not mitigated by design:** `application.properties` sets `spring.kafka.consumer.group-id=portfolio-service`, so a new `@KafkaListener` that omits `groupId` joins the Portfolio group and splits its partitions without any error — messages appear to go missing at random. `MarketDataListener` sets `groupId` explicitly. **Residual:** re-arming is unbounded, so a customer can cause repeated messages to their own address up to the notification row cap | Cap and idempotency: **Verify at build** (P4, P8). Group id: **mitigated** by a test that fails if any `@KafkaListener` in the Trade API lacks an explicit `groupId` or reuses a reserved id (P7). Re-arm volume: **accepted** — the only recipient is the customer's own resolved address, and the 10 000-row cap bounds the table; the team took this decision in `0005` |

| A07 Identification and authentication failures | Platform | Yes | The four modules add no login, registration or token issuing; identity comes from the existing verifier. `JwtValidator` requires a valid signature, expiry (checked by the library and again explicitly), a subject and at least one role, and every failure returns the same body `{errorCode: "AUTH-401", message: "Unauthorized"}` without naming the cause. ## Where the categories landed differently

| Category | Preferences | Notifications | Watchlists | Portfolio |

| A01 | Reads and writes one account's record; the account in the path must match the claim; owner of the one route that touches `auth_db.users` | Route is a history read; the outbound path is the one place a mistake sends data to someone else, so the resolver is the only source of the recipient | Alerts and watchlists belong to one account; the market-data consumer has no caller and therefore no token, so the per-account check applies only to the HTTP routes | Existing routes already check the claim; the contract routes in `portfolio-api.yaml` add a second path form that needs the same check |
